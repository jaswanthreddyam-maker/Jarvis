Executive Summary
This report outlines a comprehensive design for a Jarvis-like voice assistant running locally (with optional
cloud fallback) on a laptop (16 GB RAM, RTX 4050 GPU). The assistant will use a hybrid multi-agent
architecture: Anthropic Claude Opus 4.6 for high-level reasoning (intent parsing, task planning, tool usage)
and OpenAI ChatGPT/Codex for code generation and review. Voice I/O is handled by wake-word detection
(Porcupine), speech-to-text (Whisper or Picovoice Cheetha), and text-to-speech (Coqui TTS). Key components
communicate via REST/IPC (or message queues) and share memory (short-term context, long-term SQLite
DB). The system includes safety/guardrail prompts, schema-validated tool calls, and rigorous testing. Below
we detail goals, architecture, folder structure, prompt design, protocols, schemas, dependencies,
integration steps, memory model, security, testing, and a development roadmap. 
1. Goals
Always-On Voice Interaction: The assistant listens for a wake-word (e.g. “Jarvis”), converts speech
to text, understands commands, and replies via synthesized voice. 
Natural-Language Understanding & Multi-Step Tasks: Use Claude Opus 4.6 to parse user intent,
plan multi-step actions, and sequence tool calls. 
Autonomous Execution: Automate tasks like opening applications, web search, file operations, and
running scripts via a Python “Action Engine.” 
Hybrid Cloud-Local Operation: Run core LLM reasoning locally (via Ollama) for privacy and speed,
but fall back to Claude (Anthropic cloud) or GPT-4o/Codex for very complex tasks if allowed. 
Developer-Agent Collaboration: Assign Claude Opus 4.6 the role of “planner/agent oracle” (multi-
step decomposition, general knowledge) and ChatGPT/Codex the role of “code-oriented
developer” (write/inspect Python scripts). Each agent follows strict system prompts and JSON
schemas for output. 
Privacy and Safety: By default operate offline (Ollama) so no data is sent externally; enforce
content filters and disallow dangerous actions via guardrail prompts.

Wake-Word Detection: Monitors microphone for a trigger word (“Jarvis”) using Picovoice Porcupine
. 
Speech-to-Text (STT): On wake-word activation, capture audio and transcribe it. We can use OpenAI
Whisper (local model) or Picovoice Cheetah (streaming on-device ASR). 
Intent Parsing: The transcript is sent to a Claude agent whose system prompt instructs it to “parse
the user’s command into a structured intent.” The agent outputs a JSON with an intent and 
parameters. 
Task Planning: Another Claude prompt takes the parsed intent and user profile/memory and
decomposes it into a sequence of sub-tasks (e.g. “search web”, “download file”, “play media”). The
output is structured (JSON steps) to guide execution. 
Code Generation/Review: For any step requiring code or scripts, we invoke the ChatGPT Codex
agent. Claude may request Codex to generate a Python script or to review existing code for errors/
security. 
Action Engine: A Python service executes each planned step. Tools include web automation (e.g.
Selenium/Playwright for browser tasks), OS control (opening apps, files, volume), system commands,
or custom scripts. This engine receives structured commands (via a JSON schema) and returns
results or errors. 
Memory & Database: A local store (SQLite) holds long-term user preferences (“likes dark mode”)
and conversation history. Claude and Codex agents can read/write short-term context (current
session) and long-term facts for personalization. 
Text-to-Speech (TTS): After action completion (or to ask clarifying questions), the assistant speaks
using Coqui TTS or pyttsx3. Responses from Claude/Codex are converted to audio locally. 
Each component runs as a separate module or microservice. They communicate via HTTP/REST APIs or an
internal message queue. This modular design follows multi-agent best practices: stateless agents, clear
protocols, and asynchronous messaging for scalability.

4. Agent Roles & Prompts
Inter-Agent Responsibilities:
Claude Opus 4.6: Acts as the “brain”. It receives transcribed user commands and context, outputs
structured intents and plans multi-step tasks. Claude is chosen for its strong multi-step reasoning
. It fills roles such as intent parser , task planner , clarifier (asking follow-up questions), and overall
supervisor . 
ChatGPT Codex: Acts as a “developer/code assistant” agent. It is invoked when code snippets need to
be written or reviewed (e.g. writing a Python script to download a file, or checking a regex). Codex’s
system prompt instructs it to output valid code or constructive feedback. 
Fallback Rules: If Claude’s local run (via Ollama) times out or fails, the system falls back to the Claude
cloud API (Anthropic). If Codex fails, a backup is using a GPT-4-like model for code. Similarly, trivial
tasks (like simple web search) can be hardcoded in ActionEngine rather than asking an agent.

5. Inter-Process Communication (IPC)
Agents and modules communicate via structured APIs: 
REST/gRPC: Each service (e.g. claude_agent.py, codex_agent.py, planner.py, 
action_engine.py) can expose an HTTP or gRPC endpoint. For example, the main loop can send
the user query to the Claude agent via REST and parse the JSON reply. Using REST is simple (Flask/
FastAPI) and matches the request/response pattern. 
Message Queues: For robustness and decoupling, a message broker (e.g. RabbitMQ, Redis Pub/Sub)
can queue tasks between agents. This allows asynchronous processing (e.g. STT running
continuously, task planning queued separately). Each message is JSON with a type
(intent_parse, plan_task, execute_action) and payload. 
Data Contracts: Define JSON schemas for all inter-component messages. For example, an “Intent”
message:
{
"user_id": "123",
"transcript": "turn off the lights",
"timestamp": 1681520000
}
and a “Plan” message:

Using JSON Schema ensures each service validates inputs before processing. 
Concurrency: Audio capture runs in its own thread/process. Once the wake word is detected, the

actions may also run in separate threads to allow streaming TTS during long tasks.

[WakeWord] --(event)--> [ASR] --(text)--> [Intent Agent] --(intent JSON)--> 
[Planner Agent] --(plan JSON)--> [Action Engine] --(action results)--> [Speech

7. Libraries, Models, and Environment
Python Libraries:
ASR and Wake Word:openai-whisper (for Whisper models) or pvcheetah (Picovoice ASR) and 
pvporcupine . Also pvrecorder, pvspeaker for audio I/O. 
TTS:coqui-tts (latest 0.27.x, install via pip install coqui-tts) or fallback pyttsx3. 
LLM Agents:anthropic library (Claude API), openai (ChatGPT/Codex API). For local LLMs: 
ollama runtime must be installed (or run as a container). 
Automation:selenium or playwright for web control; requests/ beautifulsoup4 for
HTTP; sqlite3 (built-in) for DB; standard libs (os, subprocess, json). 
Utilities:fastapi or flask (for REST endpoints), pika or redis (for messaging), pytest
(for testing). 
Models:
Whisper: Use a model that fits 8–10GB VRAM. E.g. small.en (~2GB VRAM), medium.en (~5GB)
. Large (10GB) may not fit on RTX4050. 
Local LLM (Ollama): Install models like Mistral (7B, ~13GB) or LLaMA variants. Ollama can load
models partly on CPU/GPU. Memory tuning: with 16GB RAM + GPU, set Ollama to use ~80% GPU
memory. 
Claude/Codex: Use Claude Opus 4.6 or cloud Sonnet (as available) via Anthropic API. For code, use
GPT-4o or Codex (e.g. gpt-4o-code model). 
Hardware/OS:
GPU: NVIDIA RTX 4050 (≈8GB VRAM, Ada Lovelace). Enable GPU for Whisper and LLM inference. 
CPU/RAM: 16 GB RAM, modern multi-core CPU. Linux/macOS/Windows all supported, but Linux
often simplest for audio drivers.

8. Integration Patterns
Wake Word + ASR Loop: Use pvporcupine with pvrecorder to continuously read audio frames
. On detection, switch to STT. For Whisper , capture audio until silence (via a VAD like Picovoice
Cobra or silero VAD) and then transcribe. Alternatively use streaming ASR (pvcheetah) for lower
latency . 
LLM Invocation: Implement a client in Python that sends prompt messages to Claude/Codex APIs.
For local Ollama, use its HTTP API (e.g. requests.post('http://localhost:11434/ask', 
json={...})). Always include system prompts from prompts/*.txt. Handle streaming vs full
responses as needed. 
Tool Calls: When Claude outputs a plan with tool calls, parse the JSON and dispatch to
corresponding Python functions. For example, if planner returns 
{"tool": "open_url", "url": "https://youtu.be/..."}, call webbrowser.open(url).
Return any results back as JSON for the agent to see. 
Memory Access: Expose a simple API (or module) for agents to read/write memory. For example,
Claude’s prompt can say “Check memory for user likes.” The code uses memory_manager.py to
query SQLite. 
Offline vs Online Modes: By default set Ollama to local-only (OLLAMA_NO_CLOUD=1) . If an
agent requires web search, either use local knowledge base or call an online API (bing/google) if
allowed. Provide a flag to enable/disable internet usage. 
9. Memory Design
Short-Term Memory: In-process state (e.g. list of recent exchanges) for the duration of a
conversation. Not persisted. Used to maintain context across multi-turn dialogs.

10. Security & Privacy
Local-First Processing: With Ollama and local Whisper/TTS, no audio/text leaves the machine by
default . If cloud APIs are used, encrypt or hash any sensitive parts, and never log raw transcripts.
API Key Safety: Store API keys in environment variables or .env (excluded from source control).
When calling OpenAI/Anthropic, use HTTPS with bearer tokens. Do not hardcode keys in code. 
Content Filtering: System prompts include strict rules: refuse illegal or unsafe requests. Use
Claude’s built-in content filters for extra safety. For example, add a policy in prompts: “If the request is
malicious or disallowed, respond with a refusal.”
Execution Sandbox: For any code execution (run_code), run in a restricted environment (e.g.
limited permissions). Avoid executing arbitrary user code. Validate tool call parameters (e.g. disallow
filesystem writes outside a safe directory). 
User Privacy: Do not store sensitive PII. If storing personal data, encrypt it in the DB. Clearly inform
the user if any data is being sent to the cloud. 
11. Testing Checklist
Unit Tests: Use pytest to test individual components. For example: 
Wake Word: Supply prerecorded audio with/without the keyword and assert detection
( pvporcupine.process). 
ASR: Given a short speech clip, test the Whisper transcription output. 
Agents: Mock API responses: feed a prompt to Claude/Codex and verify the output matches schema
(e.g. valid JSON intent). 
Tool Functions: Test each action function (search, file ops) to ensure correct output or side-effects. 
Integration Tests:
Voice Pipeline: Simulate “wake word → command → action → response”. For example, play an audio
file of “Jarvis, open Google Chrome.” Check that the system correctly transcribes and the browser
opens. 
Agent Flow: Feed a hard-coded command string into the full pipeline (skip audio) and assert final
outcome. 
End-to-End (E2E):
Run the assistant, speak various commands, and verify expected behavior . Create test cases like: 
Turn on/off hardware (if applicable)

offline tasks).
